# SwiftSlate desktop security and quality audit

**Audit date:** 2026-11-05  
**Target:** SwiftSlate Python/Win32 desktop application and `SwiftSlate-Setup-x64.exe`  
**Audited baseline:** Git commit `ebfdc937eab840a0cc9c9e0a0e7d525be7ab4b00` plus the remediations described below  
**Validated release source:** Git commit `99e3069d9f6d6ae004b35cd375c2c6e9413519da`

**Platform priority:** Windows x64; Linux was used for platform-independent analysis and tests

## Executive summary

The audit covered correctness, regression risk, security, privacy, dependencies and build provenance, Windows integration, concurrency, accessibility, performance, packaging, and maintainability. It found no known unresolved critical vulnerability. The most consequential findings were a reusable dashboard capability exposed in a URL, mutable or unhashed build inputs, shell-based local-command execution, and incomplete loopback-server request validation. Those issues have been remediated and protected by regression tests.

The dashboard now exchanges a one-time URL-fragment capability at `/api/v1/session` for a fresh, API-scoped `HttpOnly` cookie. Its loopback server also validates `Host`, `Origin`, and Fetch Metadata; limits request bodies; applies socket timeouts; blocks encoded traversal; and serves a restrictive Content Security Policy. Windows Python build inputs are version- and hash-locked, GitHub Actions are commit-pinned, and the fixed Inno Setup package version is installed with checksum enforcement. Local commands no longer invoke a shell. Legacy plaintext API keys are automatically moved to current-user DPAPI storage.

The platform-independent release gates pass: 51 Python tests were collected (48 passed and 3 Windows-only tests skipped), all six frontend tests pass, strict TypeScript and Python compilation pass, Ruff and Bandit report no findings, npm and pip dependency audits report no known vulnerabilities, and the production dependency license review found only permissive licenses. The post-remediation Windows installer pipeline result is recorded in [Windows release validation](#windows-release-validation).

## Scope and method

Reviewed components:

- Win32 Raw Input capture, clipboard/`SendInput` replacement, tray lifecycle, startup behavior, and singleton handling;
- configuration loading, hot reload, current-user DPAPI credential storage, migration, logging, and redaction;
- all ten provider integrations, endpoint validation, model discovery, timeout/error behavior, and custom endpoints;
- loopback dashboard server, WebView2 host process, authentication, request parsing, static assets, and browser security policy;
- React/TypeScript interface, onboarding, keyboard operation, dialogs, error states, and local style previews;
- PyInstaller one-directory freeze, WebView2 bootstrapper handling, Inno Setup install/upgrade/uninstall behavior, and artifact hashing;
- Python and npm dependency graphs, third-party licenses, workflow action references, and downloaded build tools.

Methods included manual code and threat-model review, diff review, unit and integration tests, static analysis, dependency vulnerability queries, license inspection, a production frontend build, packaged self-tests, and clean Windows install/uninstall automation. The review was not an independent penetration test or a formal cryptographic verification.

## Threat model and trust boundaries

SwiftSlate intentionally observes system-wide keyboard input and replaces typed command text. That capability is sensitive by design. Provider prompts leave the device only when the user selects a remote provider. Provider credentials are encrypted at rest for the current Windows user with DPAPI, excluded from dashboard responses, and redacted from application logs.

The dashboard binds only to loopback and is opened on demand. Browser pages and other local applications are treated as untrusted. A process already running as the same Windows user remains outside the security boundary: it can generally inspect that user's processes, use the user's DPAPI context, alter user-writable files, or synthesize input. Administrator- or kernel-level compromise is also out of scope.

## Findings and remediation

| ID | Original severity | Finding | Remediation and evidence | Status |
|---|---|---|---|---|
| SS-01 | High | The dashboard used a reusable bearer value in the URL query and frontend authorization headers. URL/history/process exposure could unnecessarily retain that capability. | A cryptographically random, one-time capability is now placed after `#`, exchanged by `POST /api/v1/session`, invalidated immediately, and replaced by a fresh `HttpOnly`, `SameSite=Strict`, `/api` cookie. Sessions rotate for every WebView launch and old bootstrap/session values fail regression tests. | Fixed |
| SS-02 | High | Python packaging requirements were version-pinned but not artifact-hash-locked; workflow actions used mutable tags; the Inno tool version was not fixed. | The complete Windows CPython 3.13/x64 graph is in `requirements-build-lock.txt` with SHA-256 hashes and is installed with `pip --require-hashes`. Actions use immutable commit SHAs. Inno Setup is fixed at 7.1.1 and its official installer is checked against a pinned SHA-256 digest. | Fixed |
| SS-03 | High | `replacer-shell` launched user-configured local commands with `shell=True`, adding command interpreter expansion and quoting behavior beyond the configured executable. | Windows `CommandLineToArgvW` parsing and direct `subprocess` execution replace the shell. Empty/invalid command lines fail closed. Installer upgrade/uninstall process termination also invokes `{sys}\taskkill.exe` directly rather than `{cmd}`. | Fixed |
| SS-04 | Medium | Loopback authentication did not fully constrain DNS-rebinding/CSRF-style requests or browser navigation context. | The server now checks the exact loopback `Host`, requires same-origin Fetch Metadata for every API request and the exact `Origin` for mutations, rejects cross-site requests, and verifies cookie authentication. Tests cover wrong host, wrong origin, cross-site metadata, and valid desktop requests. | Fixed |
| SS-05 | Medium | The HTTP server lacked explicit body-size and socket-time limits, and static path handling did not explicitly reject all encoded traversal forms. | API bodies are capped, malformed/oversized bodies are rejected, accepted sockets have timeouts, and decoded paths containing traversal segments are rejected. Tests cover oversized requests and encoded traversal. | Fixed |
| SS-06 | Medium | A file-based singleton lock could be stale or race during concurrent starts and did not naturally scope ownership to a Windows logon session. | A kernel-managed, session-local Win32 named mutex now controls the singleton. A source regression requires the named-mutex API and rejects the former lockfile call. | Fixed |
| SS-07 | Medium | Configuration reload could replace command/provider state while a text replacement was active, and dashboard/tray/inline entry points used a non-atomic shared boolean to reserve the one processing slot. | A nonblocking processing mutex now serializes all transformation entry points. File changes are deferred while processing and applied when the active replacement finishes, avoiding mixed old/new state during one operation. | Fixed |
| SS-08 | Medium | Credentials left by an older plaintext configuration format remained plaintext until the user manually re-saved settings. | Successful load now migrates recognized legacy root and provider keys into current-user DPAPI blobs and atomically rewrites configuration without plaintext values or migration markers. Regression tests cover root-only, provider-only, and mixed protected/plaintext files without falling back to stale plaintext. | Fixed |
| SS-09 | Medium | Modal and onboarding keyboard behavior lacked complete focus containment and initial focus; modal dialogs also lacked Escape handling and focus restoration. Some controls had ambiguous IDs/labels. | Reusable dialogs and onboarding now trap Tab/Shift+Tab and select initial focus. Dismissible dialogs support Escape and restore invoking focus; required onboarding cannot be accidentally dismissed. Controls use unique accessible IDs, and search can be focused from the keyboard. An axe-core smoke test reports no automatically detectable violations (color contrast is excluded because jsdom cannot calculate rendered contrast). | Fixed |
| SS-10 | Low | Some async command toggles and clipboard writes could reject without a user-visible failure; the always-on tray setting appeared configurable. | Rejections now reach the existing error presentation path, clipboard operations report failure, and the required tray behavior is displayed as a disabled control. | Fixed |
| SS-11 | Low | Unused TypeScript symbols were not rejected, allowing dead UI code to accumulate. | `noUnusedLocals` and `noUnusedParameters` are enabled; the current tree passes strict type checking. | Fixed |
| SS-12 | Low | The installer created a placeholder `HKCU\...\Run` value so it could delete startup registration later; an install or silent upgrade could transiently reset an application-owned preference to invalid `REG_NONE` data. | Setup no longer writes the startup value. The application alone applies the saved preference, while uninstall explicitly removes the value through `RegDeleteValue`. | Fixed |

## Security and privacy controls after remediation

- API keys are current-user DPAPI protected at rest and are never returned in dashboard snapshots.
- Logs redact known credentials and authorization material; diagnostics expose only redacted records.
- The local API requires a fresh launch-specific session and rejects stale sessions.
- Mutation requests require a valid cookie plus same-origin browser context.
- Static files are constrained to the bundled UI root and are served with `nosniff`, frame denial, referrer restrictions, and a restrictive CSP.
- Provider and model calls use bounded timeouts and endpoint-scheme validation.
- Local command execution is explicit and shell-free.
- Configuration writes are atomic; a processing mutex serializes transformations, and active work defers hot reload.
- The WebView process exists only while settings are open, avoiding permanent WebView2 idle overhead.

## Dependency and license review

### Python build graph

`requirements-build-lock.txt` contains 15 exact distributions with explicit SHA-256 artifacts for Windows x64/CPython 3.13. A `pip-audit` review of the platform-resolved graph reported **0 known vulnerabilities**. Build installation uses `--require-hashes` both locally and in CI.

### Frontend graph

`npm ci` and `npm audit --audit-level=moderate` reported **0 known vulnerabilities**. Production dependencies and transitive packages reported permissive licenses (MIT, Apache-2.0, BSD, or ISC combinations). The dev-only `axe-core` test dependency is MPL-2.0 and is not present in `ui_bundle` or the installed application. The scanner labels the private root workspace `UNLICENSED`; the root package metadata and repository license identify MIT, and this label did not apply to a third-party dependency.

### Build services and tools

GitHub-hosted actions are pinned to immutable commits. The official Inno Setup 7.1.1 x64 installer is downloaded from its GitHub release and accepted only when it matches the pinned SHA-256 digest. The Microsoft WebView2 bootstrapper is downloaded during the Windows build and accepted only when Windows reports a valid Microsoft Authenticode signature.

## Residual risks and release notes

| Risk | Rating | Treatment |
|---|---|---|
| The application and installer are not Authenticode-signed, so Windows may display an unknown-publisher/SmartScreen warning and users cannot verify publisher identity. | Medium | Obtain a trusted code-signing certificate, sign both the executable and installer, and verify signatures in CI before public release. SHA-256 files provide integrity only when obtained through a trusted channel. |
| Evergreen WebView2 and the build-time Microsoft bootstrapper are external moving components; Microsoft signature validation proves publisher/integrity but not a fixed bootstrapper digest. | Medium | Continue signature verification. For controlled deployments, mirror and pin an approved Evergreen Standalone installer under an explicit update policy. |
| A malicious process already running as the same user can interact with input, user-writable configuration, process memory, and the user's DPAPI context. | Medium | This is an OS trust-boundary limitation. Use standard endpoint protection and least-privilege accounts; do not represent DPAPI as protection from same-user compromise. |
| Remote providers receive selected prompt text and may retain it according to their own policies. A custom provider URL deliberately allows user-selected destinations. | Medium | Keep provider choice explicit, show the endpoint, document provider privacy terms, and avoid sending secrets in commands. |
| Provider APIs, model identifiers, quotas, and response schemas can change independently. Automated tests do not make paid live calls. | Low | Keep bounded errors and model refresh behavior; run opt-in credentialed provider smoke tests before major releases. |
| Automated accessibility checks cannot validate rendered color contrast, Windows high-contrast mode, screen-reader announcements, 200% zoom, or every modal path. | Low | Complete manual keyboard, Narrator, high-contrast, and scaled-display checks on the signed release candidate. |
| PyInstaller/Inno output is reproducible from locked inputs at a functional level but is not claimed to be bit-for-bit reproducible across runner images and timestamps. | Low | Record hashes and runner/tool versions for every release; investigate deterministic timestamping if binary reproducibility becomes a requirement. |
| Uninstall removes the program and startup entry but intentionally preserves `%LOCALAPPDATA%\SwiftSlate` for reinstall/upgrade continuity; that directory can retain commands, preferences, DPAPI blobs, and opt-in debug logs. | Low | Document the behavior and delete that directory manually when a full data purge is required. Never remove user data silently during an upgrade. |
| Redaction covers known structured secrets but cannot guarantee removal of arbitrary secret text a user types into diagnostics or provider errors. | Low | Keep diagnostics local by default and require user review before sharing logs. |

## Release decision

**Approved against the audited automated gates.** The remediated source and Windows installer pipeline pass, and there is no known unresolved critical or high-severity finding. The recorded artifact is suitable for controlled testing or distribution where the unsigned-publisher warning is explicitly accepted. Authenticode signing remains the priority before broad public distribution.
